The pipeline

How a change happens

This is the real sequence the shop's Claude sessions follow, written down in its repositories. Each step is a rule, a file or a script you could point to.

  1. He says what he wants, in his own words

    The owner types into the Claude session on the computer in front of him: the plant PC during the shop day, his home PC in the evening. His words are copied into the desk log, the commit message and the test's heading, typos and all.

  2. Claude searches the code instead of reading all of it

    Every one of the live system's 3,973 functions carries a keyword label from one shared list, so a search returns the function, its file and line, and a one-line purpose. Past work is found the same way, by searching the desks' logs.

  3. It changes the live system's code, in place

    The change goes into the existing functions on the live system's branch. Customer and money records are never changed by editing code; those go through the app's own functions, on its activity log.

  4. It writes a proof named after the request

    A new numbered section goes at the end of the test file, and its heading quotes the request, like §695 — A DRAWER ALERT IS $1 OR MORE, from the owner's "i don't want to get cash drawer alerts for any amount less than $1". Every proof needs a negative control: a check that shows it would catch the old behavior. Since the switch, 91 proof sections have been added (§616 to §706), and 43 of the 50 headings that group them quote the owner.

  5. It runs every proof, then commits

    The whole suite takes about 10 minutes and must end "0 failed"; on Oct 12 that was 1,226 passed. It also fails if the code's search index is out of date. The commit carries the request, the proof number and a Claude co-author line. Helper agents in a multi-agent run never push or deploy.

  6. The server checks it again, and undoes it if needed

    The deploy script refuses unless the change is committed and pushed. It runs the whole suite again on the server, in the live system's time zone, and refuses on any failure with nothing changed. Then it puts the build live; if the new build doesn't answer as itself within 30 seconds, the previous one goes back live by itself. The 5 newest previous builds are kept for a one-line rollback, and a last check confirms the public address is serving this exact build.

  7. It goes live at 7 PM Central, unless the owner says "now"

    The rule is that new builds go live after the shop day, and when the counter needs a fix right away, the owner says so. It is a rule the sessions follow, not something the script enforces, and many fixes since the switch have gone live during the day.

  8. It writes down what happened

    A new entry goes at the top of that desk's log: what the owner asked, what changed, which build is live, what was checked, and what is still waiting on him. It is committed, so the next session at any desk can find it.

One Claude session per shop computer

Four desks: the owner's PC, the plant, the Hot Springs counter and the Arkadelphia counter. Each keeps a short file of facts about that machine, a log with the newest entry first, and a to-do folder. Finished to-dos are moved to a done folder, never deleted. All four have logged since the switch.

Guardrails

Why it's safe to let an AI touch a live business

The rules below are written into the shop's repositories, and every Claude session starts from them. Several are also enforced by the software itself.

“The live shop wins, always.”

The prime directive of the safety charter the owner asked for on Sept 12, 2026 ("build the claude intro that keeps the AI safe working on a live production environment"). It also says a plain-English request is a spec, not a merge to live.

Money stays with the owner

No refund, void or re-charge from a guess: the card log, the processor's funding and the POS records are checked first. On the shop's server, refunds, voids, write-offs and account credits are owner-only, and store credit, clock edits and staff changes need a PIN the server checks. Claude can't hold or type a PIN.

When the owner asked Claude to credit back repeat fees, Claude built it so its desk can only suggest each credit; he approves each one with his own PIN, and a proof shows a desk that tries to give credit itself is refused.

A proof on every change, and proof the proof works

"A test that cannot fail is not evidence." Every new proof carries a negative control showing it would catch the old behavior. The phrase "negative control" appears on 914 lines of the 26,333-line proof file.

The server checks again, and rolls itself back

Deploys go only through the deploy script. It refuses a stale, uncommitted or failing build, keeps the previous builds, and puts the last one back by itself if the new one doesn't answer. At least 6 deploys have been refused since the switch; the shop kept its running build each time.

Live at 7 PM, after the shop day

Unless the owner says go. To be plain about it: this is a discipline, not a lock. Many fixes have gone live during the day while the counter waited on them, and the logs record his go for some, not every one. One went live by accident: on Oct 7 a build went live at 4:26 PM because of a time-zone trap.

Data fixes go through the app, on the record

Customer and money data change only through the app's own functions, so every change lands on its activity log. Each fix is a script with a savepoint, a dry run, the change and a read-back. Claude's changes are recorded as Claude's desk, a temporary station revoked afterward, because the owner asked for exactly that: "you should be using your own access that says claude did it, not brayden".

Nothing is deleted, and nobody is merged on a guess

In the live system every change is a fact recorded once, never edited or erased. A record is retired, never hard-deleted, and a mistake is fixed by adding a new fact.

Customers who share a phone are never merged. On Oct 12 a merge the owner had approved, based on a wrong description, was stopped when the dry run showed a person and his company account. Nothing was merged.

Secrets never go in the code

Keys live only on the server and are never printed, pasted, committed or typed. Card numbers never reach the POS; it holds the processor's tokens only.

Anything Claude would send to customers or the public waits for a yes

Texts or e-mails Claude would send to customers, public web pages, DNS, scheduled tasks and lasting settings need the owner's explicit yes first. DNS changes are add-only.

The old system is one flip away

The shop's first system is frozen and locked, so it can't charge, text or e-mail, but it still runs for looking up history, and the steps to flip back are written down.

Honest limits

What this doesn't do

If you're deciding whether to work this way, these matter as much as the numbers.

  • A person still decides.The owner approves money (refunds, and store credit with his own PIN), anything sent to customers, and anything public. The server refuses Claude's desk on privileged money actions.
  • It needs someone who will say what they want.Almost every change since the switch began with the owner hitting something at the counter and saying so. Fixes Claude found on its own are the minority.
  • Claude makes mistakes, and the rails catch many but not all.From the logs: on Oct 1 a "dry run" actually sent its changes; on Oct 5 a change sent wash-and-fold tickets to the wrong screen (fixed Oct 6); on Oct 7 a build went live at 4:26 PM instead of 7 PM; on Oct 12 a customer merge asked for on a wrong description was stopped only by the dry run.
  • The 7 PM rule is a discipline, not a lock.Many fixes since the switch went live during the day, while the counter waited on them. The logs record the owner's go for some (Oct 1, Oct 7), not for every one.
  • Checking is slow, and sometimes noisy.The suite takes about 10 minutes, then runs again on the server for every deploy. Timing proofs on the busy server have refused some deploys over noise, not faults.
  • The system the shop runs today isn't in customPOS yet.Its plan is written, but none of its code is here. Today customPOS offers the builder and the Single-PC Edition, which is the shop's first system.
  • The shop's own code is private.customPOS publishes only scrubbed exports, with no customer or staff data.
  • It isn't free.AI usage costs money. The owner keeps large multi-agent runs for build work and hears the cost first; the Oct 10 Single-PC build, for example, used a 7-agent run of about 2.3 million tokens.
  • Staff run the counter.Claude edits code and data only when asked, and never runs the shop by itself.

Questions, answered plainly

Is a real shop actually running on this?

Yes. Ozark Cleaners, a two-store wet cleaner in Arkadelphia and Hot Springs, Arkansas, has run on its own software since summer 2026; the first commit was on June 20. It moved to its current multi-computer system on September 30, and that system's code changed on 9 of the 12 days that followed.

Does Claude run the shop?

No. Staff run the counter. Claude changes code and data only when someone asks, and a person decides anything that involves money, customers or the public.

Can Claude move money?

No. Refunds, voids and credits are the owner's. On the shop's server those actions are owner-only, privileged ones need a PIN that the server checks, and Claude cannot hold or type a PIN. Claude can suggest a store credit; the owner approves it with his own PIN.

What happens if a change breaks something?

Most problems are caught before they go live: every change gets a proof, the whole suite runs on the shop's computer and again on the server, and the deploy is refused on any failure. If a new build does not answer within 30 seconds, the previous build goes back live by itself. Some mistakes still get through and are found at the counter; the fix then takes the same path.

Do I need to know how to code?

The shop's owner describes what he wants in plain words, and Claude Code writes the code and the tests. You do need to say clearly what you want, check the result before you rely on it, and keep backups.

Is the shop's code public?

Not all of it. The shop's own repositories are private. customPOS publishes scrubbed exports with no customer or staff data: the Single-PC Edition is the shop's first system as one file. The multi-station system the shop runs today is not in customPOS yet.

What does the AI cost?

customPOS is free. Claude is not: AI usage is paid to Anthropic under its own pricing. The shop keeps the cost down by having each desk's Claude work alone by default and saving large multi-agent runs for build work, with the cost stated first.

Is customPOS part of Anthropic?

No. Claude is made by Anthropic. customPOS is independent and not affiliated with Anthropic.
